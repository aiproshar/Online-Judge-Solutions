# The Problem Approach Framework

> A framework for coding interviews built around the single question every interviewer is really asking:
> **"What kind of engineer would this person be if they joined my team?"**

Getting the right answer is only one signal. The strongest candidates demonstrate good judgment, communicate clearly, and leave the interviewer thinking: *I'd trust this person to solve hard engineering problems alongside my team.*

---

## 1. Understand the Problem

Real engineering starts by defining the problem, not rushing to a solution.

- Reduce ambiguity before writing any code.
- Clarify requirements and confirm your understanding out loud.
- Identify constraints: input size, performance, memory, and edge conditions.
- Surface edge cases up front rather than discovering them later.

**Checklist**
- [ ] Restated the problem in my own words
- [ ] Confirmed inputs, outputs, and constraints
- [ ] Listed edge cases before coding

---

## 2. Build Algorithmic Intuition

The goal isn't just to find *an* answer — it's to show sound technical judgment in how you get there.

- Reason from fundamentals instead of pattern-matching from memory.
- Weigh the trade-offs between competing approaches.
- Explain *why* your chosen approach fits the problem.
- Compare time and space complexity out loud.

**Checklist**
- [ ] Considered more than one approach
- [ ] Discussed the options with the interviewer before committing to code
- [ ] Articulated the trade-offs
- [ ] Justified why this approach fits the constraints

---

## 3. Think Before You Type

Clean, deliberate code is a far stronger signal than repeatedly rewriting a messy solution.

- Outline the structure of your solution before writing it.
- Ask yourself: *Would I be confident reviewing this in a production pull request?*
- Favor readable, intentional code over raw speed.

**Checklist**
- [ ] Sketched the structure or plan first
- [ ] Named variables and functions clearly
- [ ] Reviewed the code as if someone else had written it

---

## 4. Validate Your Own Work

The best engineers catch their own bugs before anyone else has to.

- Test normal, boundary, and edge inputs.
- Challenge the assumptions you made earlier.
- Trace through the code with concrete values.

**Checklist**
- [ ] Walked through normal and edge inputs
- [ ] Questioned assumptions I made earlier
- [ ] Found and fixed issues before being prompted

---

## 5. Treat It Like a Collaboration

The best interviews don't feel like a test — they feel like two engineers solving a problem together.

- Narrate your reasoning as you work.
- Ask clarifying questions when you're unsure.
- Respond naturally and openly to feedback.

**Checklist**
- [ ] Narrated my reasoning
- [ ] Asked questions when unsure
- [ ] Adapted well when given hints
